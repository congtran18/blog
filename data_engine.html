1. Tại sao không lưu JSON? (Chiếc hộp rỗng): Lưu JSON blob vào database giống như bạn đi thuê kho để chứa đồ, nhưng đồ thì bé tí còn mỗi món lại bọc trong một chiếc thùng các-tông khổng lồ có in đầy đủ nhãn mác. 88% dung lượng bạn trả tiền là trả cho "tên của các thuộc tính JSON" bị lặp đi lặp lại hàng triệu lần. 2. Tại sao dùng REPLACE PARTITION? (Tráo mục lục sách): Thay vì bạn xóa trang sách cũ rồi ngồi cặm cụi chép từng dòng trang mới vào (vừa lâu vừa làm người đọc bị gián đoạn), bạn in trang mới ở một cuốn sổ nháp (staging), kiểm tra khớp số chữ 100%, rồi trong 1 tích tắc tráo tờ giấy nháp vào cuốn sách chính. Chi phí chỉ là đổi con trỏ thư mục trên ổ đĩa ($O(1)$), mất vài mili-giây.
3. Đệm 50k dòng trong RAM bằng Zero-Allocation (Khay bưng nước tái sử dụng): Người bồi bàn gom đủ 50 ly nước vào một chiếc khay cố định rồi bưng ra bàn 1 lần trong 2 giây. Sau khi giao xong, người đó không vứt chiếc khay vào sọt rác để đi mua khay mới (tránh Garbage Collection làm đứng đơ hệ thống), mà chỉ việc đặt 50 ly khác lên đúng chiếc khay đó (buf = buf[:0]). Vừa không bị đổ nước (Zero Code 209 Timeout) vừa không tốn tiền mua khay mới (Zero-Allocation Heap).

SECTION 01 EXTRACTION & DEDUPLICATION BRONZE LAYER

01. BigQuery Extraction Mechanics: Bronze Layer & Streaming vs. Finalised Tables

In our 3-tier Medallion Architecture, Google BigQuery acts as the Bronze Layer (raw, immutable event logs exported directly from mobile SDKs). GA4 exports data into two distinct table shapes in BigQuery. Understanding this dichotomy is essential to building an accurate, low-cost ingestion pipeline:

Export Shape Table Naming Pattern Availability & Quota Deduplication Characteristics Pipeline Ingestion Treatment
Finalised Daily events_YYYYMMDD Arrives morning of D+1; free tier capped at 1M events/day. Fully deduplicated and authoritative by Google. Seals day permanently (Terminal)
Streaming Intraday events_intraday_YYYYMMDD Streams continuously within seconds; no 1M event cap. May emit duplicates (measured at 0.64%). Loads as Hot (Re-synced every cycle)

1.1. The Zero-Cost QUALIFY Window Deduplication Filter

Because streaming exports can emit duplicate events over cellular retries, we deduplicate them directly inside the BigQuery SQL projection. Instead of unnesting parameters or running expensive subqueries, we partition over the five native scalar batch coordinates Google stamps on every event:

⚡ BIGQUERY INTRADAY DEDUPLICATION SQL 
-- Appended to the query ONLY for intraday tables:
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY t.user_pseudo_id, 
               t.event_name, 
               t.event_timestamp,
               t.event_bundle_sequence_id, 
               t.batch_event_index
  ORDER BY t.event_server_timestamp_offset
) = 1
  • Zero Unnest Overhead: All five fields are top-level scalar columns. We scan zero extra bytes on BigQuery, keeping scan query billing at the absolute minimum.
  • Source-Side Guarantee: 0.64% duplicate rows are eliminated before data crosses the WAN network, saving transmission bandwidth and storage.
  • Mathematical Precision: Two genuinely distinct events would have to share the exact same user, event name, microsecond timestamp, bundle sequence, and index to be wrongly collapsed — a statistical impossibility.
🎙️ Spoken Script — Explaining Extraction in Interviews

"One tricky thing with GA4 is that the streaming intraday tables have about a 0.6% duplicate rate because mobile devices retry sending on patchy cellular connections.

Instead of pulling millions of duplicate rows over the public internet and cleaning them inside ClickHouse, we push the deduplication directly to BigQuery using a scalar QUALIFY ROW_NUMBER() window filter.

Because we partition strictly over five scalar batch coordinates without unnesting arrays, BigQuery scans zero extra bytes, so we get 100% clean data before it even hits our network."

2.1. Why 50,000 Rows Per Batch?

In columnar databases like ClickHouse, inserting rows individually or in small batches of 100 creates thousands of tiny compressed parts on disk, triggering massive background merge storms. A 50,000-row batch hits the sweet spot: large enough that per-batch insertion overhead drops to zero, and small enough that multiple concurrent source goroutines buffering 50k rows remain well under 500MB of RAM.

🔬 2.2. Zero-Allocation Slicing Mechanics (buf = buf[:0])

In Go, a slice header is a 24-byte struct containing (Data unsafe.Pointer, Len int, Cap int). If we allocated a new slice for each batch via make([]*event.Row, 0, 50000), the Garbage Collector would have to continuously scan and collect millions of orphaned pointers, creating severe GC mark-and-sweep pauses.

⚡ ZERO-ALLOCATION GO SOURCE PATTERN (internal/warehouse/warehouse.go) 
// Pre-allocate once with fixed 50k capacity:
buf := make([]*event.Row, 0, batchRows)

for row := range bigqueryRows {
    buf = append(buf, row)
    if len(buf) >= batchRows {
        if err := flushBatch(ctx, buf); err != nil {
            return err
        }
        // RESET LENGTH ONLY: Capacity and underlying Heap memory pointer remain 100% untouched!
        buf = buf[:0] // Exactly 0 Heap allocations! Zero GC thrashing!
    }
}

Result: Flat memory profile, zero GC latency jitter, and sustained 100k+ rows/second ingestion throughput.

🚦 Bounded Concurrency Semaphore

Ingestion uses a buffered channel semaphore sem := make(chan struct{}, SyncConcurrency) (default 4). This guarantees multi-tenant Firebase projects never exhaust TCP socket limits or cause CPU cache contention.

🛡️ Cancellation Shielding (context.WithoutCancel)

Critical partition swap and Postgres state transitions are wrapped in Go 1.21 context.WithoutCancel(ctx). If an incoming client connection or timeout triggers, the critical swap completes atomically without corrupting state.

🎙️ Spoken Script — Explaining Decoupled Buffering & GC in Interviews

"When we first launched, we ran into ClickHouse error 209 — connection receive timeouts — on heavy traffic days.

The culprit was that our code kept an open insert batch to ClickHouse while streaming data from BigQuery over the WAN. If BigQuery stuttered for a few seconds, ClickHouse gave up and killed the connection, crashing the entire load.

To fix this, we decoupled the read and write loops in Go: we pull 50,000 rows into RAM first using a reusable slice (buf = buf[:0] to avoid GC pauses), and only when that batch is full do we open the ClickHouse connection and flush it locally in about 150 milliseconds. After that, we had zero timeouts."

SECTION 03 STORAGE OPTIMISATION SILVER LAYER

03. Silver Layer Column Shredding: Cutting Storage by 39.6x and Query Times to 45ms

In our Medallion Architecture, ClickHouse acts as the Silver Layer (conformed, deduplicated, columnar storage). Storing raw JSON documents in databases is one of the most widespread architectural anti-patterns in enterprise data engineering. Here is why:

❌ V1 ARCHITECTURE: TIMESCALEDB + RAW JSONB
  • 3,024 bytes / row total storage footprint.
  • 88% of storage (2,690 B/row) wasted on the raw jsonb column.
  • Every single row repeated the full string keys: "event_name", "user_pseudo_id", "event_timestamp".
  • 18 of 53 Metabase cards timed out (>20s) because JSON field extraction bypassed indexes.
  • Projected volume at 365B rows/year: ~1.1 Petabytes.
✅ V2 ARCHITECTURE: CLICKHOUSE COLUMN SHREDDING
  • 76.3 bytes / row total storage footprint — 39.6x reduction!
  • Shredded into typed scalar columns and 4 typed ClickHouse Maps: params_str, params_int, params_float, user_props_str.
  • Zero repeated schema keys on disk; 4.8x native columnar compression.
  • All dashboard cards resolve in 45ms – 71ms; zero query timeouts.
  • Projected volume at 365B rows/year: ~27.9 Terabytes (affordable single-node).

🎯 3.2. ClickHouse Sparse Primary Indexing & 8,192-Row Granules

Unlike traditional relational databases that maintain a B-Tree entry for every single row, ClickHouse implements a sparse primary index with index_granularity = 8192. It writes one index mark into the .idx file for every 8,192 rows.

⚡ PRIMARY KEY DEFINITION (init-clickhouse/01-schema.sql) 
CREATE TABLE analytics.events (
    app_id LowCardinality(String),
    event_date Date,
    event_name LowCardinality(String),
    event_timestamp DateTime64(6, 'UTC'),
    user_pseudo_id String,
    params_str Map(String, String),
    params_int Map(String, Int64),
    params_float Map(String, Float64),
    user_props_str Map(String, String)
) ENGINE = MergeTree()
PARTITION BY (app_id, event_date)
ORDER BY (app_id, event_name, event_date, user_pseudo_id)
SETTINGS index_granularity = 8192;

Query Skipping: Because (app_id, event_name) lead the ORDER BY key, queries filtering by event name (e.g., WHERE app_id = 'ios_pro' AND event_name = 'ad_reward') skip 99.8% of granules on disk without decompressing them, enabling sub-50ms execution!

🎙️ Spoken Script — Explaining Column Shredding in Interviews

"The biggest win on this project came from getting rid of raw JSON.

In our v1 database, we were storing the full event as a JSONB blob in Postgres. When we analyzed disk usage, 88% of our storage was literally just repeated string keys — things like 'event_name' and 'event_timestamp' written millions of times.

So we shredded every event: core fields became typed columns, and dynamic parameters went into four typed ClickHouse Maps for strings, ints, and floats.

That alone shrunk our storage by nearly 40x — from 3,000 bytes down to 76 bytes per row — and dropped dashboard queries from 20-second timeouts to around 45 to 70 milliseconds."

SECTION 04 IDEMPOTENT ATOMICITY PRE-SWAP QUALITY GATE

04. The Atomic Load Path: Staging Table, Quality Gates & O(1) REPLACE PARTITION

In high-volume analytics, long-lived transactions are an operational nightmare. Here is how we achieved zero-downtime, lock-free ingestion with Exactly-Once Semantics (EOS):

🚀 The 4-Step Quality Gate Ingestion Protocol

STEP 1
Clear Staging Partition: Drop any leftover partition in events_staging from previous aborted runs: ALTER TABLE events_staging DROP PARTITION (app_id, event_date);
STEP 2
Buffer & Stream into Staging: Stream 50,000-row RAM batches into events_staging. Zero locks are held on the production events table; Metabase continues serving dashboards uninterrupted.
STEP 3
Pre-Swap Quality Gate Assertion: For finalised daily tables, compare written count vs BigQuery reported count: if stagingWrittenRows != bigQueryTotalRows { dropStaging(); return ErrDataMismatch; } If mismatched, the staging partition is dropped immediately — corrupt data NEVER touches production.
STEP 4
Atomic O(1) Metadata Partition Swap: Swap the validated staging partition into production in 15ms: ALTER TABLE events REPLACE PARTITION (app_id, event_date) FROM events_staging; ClickHouse re-links physical disk part hardlinks instantly. The new day becomes visible atomically with zero query locks.
🎙️ Spoken Script — Explaining Atomic Swaps & Quality Gates in Interviews

"Another big issue with the old system was that loading a single day took over 4 hours inside one massive transaction, locking tables and making dashboards crawl.

In ClickHouse, we completely separated loading from querying: we ingest batches into an events_staging table where nobody can see it.

Once the batch is fully written, we run an automated sanity check against BigQuery's reported row count. If it matches, we execute an ALTER TABLE REPLACE PARTITION.

Because it's a metadata-only swap, it takes about 15 milliseconds. Dashboard users never experience a lock, and if a load ever fails halfway, production is completely untouched."

05. Hot/Sealed Lifecycle & Automated Backfill Self-Healing

GA4 exports evolve over time: intraday tables stream today's events, finalized tables seal yesterday's events, and historical days occasionally receive late-arriving backfills. Here is how our state engine self-heals:

                                           │

  • Zero Human Intervention: When Google backfills historical mobile attribution days (e.g., D-3 or D-7), the system automatically detects the desync, resets the partition, and swaps clean data.
SECTION 06 GOLD LAYER BACKFILL-SAFE ROLLUPS

06. Gold Layer: Multi-Tier Derived Rollups & The Materialized View Trap

In our Medallion Architecture, Gold Layer marts serve fast BI dashboards. 90% of business questions (cohort retention, daily active users, revenue per user) do not need individual click events. We compute pre-aggregated rollups inside the load path:

⚠️ The ClickHouse Materialized View Trap (Why We Rejected MVs for Rollups)

Many data engineers mistakenly assume ClickHouse Materialized Views (MVs) operate like PostgreSQL materialized views. They do not.

  • MVs are Insert Triggers: In ClickHouse, an MV is merely a trigger that runs on incoming inserted blocks.
  • The Backfill Disaster: If you drop or swap a partition on the base table (or re-ingest a historical day due to a Google backfill), the Materialized View DOES NOT drop or recalculate the old partition! It blindly inserts new aggregated rows, resulting in silently duplicated metrics and corrupt dashboards.
  • Our Production Solution: We compute derived rollups (such as user_daily) as a formal step immediately following the partition swap, writing to a staging rollup table and performing an atomic REPLACE PARTITION on user_daily. This guarantees 100% backfill immunity.

✅ The user_daily rollup table is ~125x smaller than raw events, allowing Metabase to load 90-day retention and cohort heatmaps in under 40 milliseconds!

SECTION 07 ADVANCED DATA ALGORITHMS EDGE CASE ENGINEERING

07. Edge Cases & Advanced Algorithms: Midnight Sessions & Median Times

Production data engines are distinguished by how they handle ugly, messy real-world edge cases:

🌙 Midnight-Crossing Sessions (prevDayFlowDue)

When a user opens an app at 23:55 and closes it at 00:15, events straddle two date partitions. The session's outcome lands in today's partition. Our engine implements prevDayFlowDue(): when today's intraday partition lands, it automatically triggers an auxiliary rebuild of yesterday's flow facts, ensuring accurate session classification.

⏱️ Median Funnel Time (Pairwise Differences)

Subtracting two step median times can result in negative numbers if step populations differ. We calculate pairwise time differences inside each individual session first, and only then take quantileExact(0.5) over those differences. Sessions missing either endpoint or arriving out of order are cleanly dropped.

🧪 A/B Testing Net Revenue Join Engine

To determine which app variant drives true business value, the engine joins ad revenue and store in-app purchases after platform fees, taxes, and refunds. It computes p-values, Sample Ratio Mismatch (SRM) checks, and sample size requirements to give product teams confident decisions.

SECTION 08 METADATA BOOKKEEPING ACID RESUME LOGIC

08. Postgres sync_state: The "Swap First, Mark Later" Rule

ClickHouse is an analytical OLAP engine lacking distributed two-phase commits. We maintain metadata bookkeeping in a co-located Postgres database:

  • Per-Day State Granularity: One row per (app_id, event_date) tracks lifecycle: running ➔ hot ➔ success ➔ failed. A failed day never blocks subsequent days; the next cycle retries it cleanly.
  • The 'Swap First, Mark Later' Rule: We execute the ClickHouse REPLACE PARTITION first, and only once it succeeds do we record success in Postgres. If the worker crashes between the swap and the mark, the worst-case scenario is a redundant re-load next cycle — which is 100% safe because the swap is idempotent. Marking first would risk reporting incomplete data as final.

🔥 STAR Case 1: The TimescaleDB JSON Storage Explosion & Dashboard Timeout Crisis

Incident Response

Situation: In our v1 architecture, we stored GA4 events in TimescaleDB with a raw jsonb column. At 4.5M rows, storage exploded to 3,024 bytes per row (88% of disk was repeated JSON keys). 18 out of 53 Metabase dashboard cards timed out completely (>20s), and running a single COUNT(DISTINCT) took several seconds.

Task: Re-architect the warehouse layer to cut storage by at least 10x and bring all dashboard queries under 500ms.

Action: I migrated the analytical layer to ClickHouse and designed the Column Shredding model. We decomposed JSON blobs into explicit typed columns and 4 typed Maps, with hot metrics materialized on insert. We also created the user_daily pre-aggregated rollup table.

Result: Storage per row dropped from 3,024 to 76.3 bytes (a 39.6x reduction). Dashboard query latency dropped to 45ms – 71ms with zero timeouts, while exact distinct user calculations took just 71ms.

⚡ STAR Case 2: Eliminating ClickHouse Code 209 (receive_timeout) Outages

Pipeline Reliability

Situation: On multi-million row days, our Go loader frequently aborted with ClickHouse error Code 209. The root cause was that the code kept an insert batch open while reading chunks from BigQuery over the internet. A slow read window left the insert connection idle past ClickHouse's receive timeout, killing 4-hour ingestion jobs.

Task: Decouple the cloud read pace from the local database insert clock to guarantee 100% completion.

Action: I re-architected the loader to accumulate a full 50,000-row batch in Go memory before touching ClickHouse. Once full, the batch opens and transmits locally in milliseconds, then immediately closes.

Result: Completely eliminated Code 209 timeouts across all applications. Network stalls on BigQuery no longer affect database insert connections.

🔄 STAR Case 3: Detecting & Self-Healing Silent Google Analytics Backfills

Data Correctness

Situation: In production, we discovered that historical days previously marked 'success' had missing events. Google had backfilled late-arriving events into BigQuery days after the fact (a day grew from 63,197 to 75,313 rows), leaving our warehouse out of date without anyone noticing.

Task: Build an automated self-healing mechanism that detects Google backfills without running expensive query jobs.

Action: I designed an automated metadata polling loop. Every sync cycle, the engine queries BigQuery table metadata (which is free) and compares lastModifiedTime against what Postgres recorded. If they diverge, the day automatically re-queues for a clean reload.

Result: 100% automated self-healing. The pipeline caught and resolved the 75k-row backfill immediately with zero human intervention.

🌙 STAR Case 4: Solving Midnight-Crossing Session Attribution in User Journeys

Analytics Engineering

Situation: In mobile apps, hundreds of user sessions cross midnight (e.g. 23:50 to 00:20). User journey and funnel cards showed artificial drops because the session conversion events landed in the next day's partition.

Task: Accurately capture multi-day sessions in flow rollups without rebuilding the entire historical database every cycle.

Action: I implemented prevDayFlowDue(): whenever an intraday load runs for today, it evaluates whether yesterday's flow facts should be re-built using evidence from both partitions. We cached build timestamps to throttle this to once every few hours.

Result: Corrected conversion attribution across midnight sessions while saving 90% of rollup computational overhead.

Top 20 Rapid-Fire Data Engine & Warehouse Interview Q&A

Q01

Why choose ClickHouse over TimescaleDB or Postgres for an analytics warehouse?

⚠️ TRAP: Saying ClickHouse is just 'faster' without citing columnar storage principles.
▼

"TimescaleDB is still row-oriented underneath. When calculating metrics like DAU or MAU across billions of rows, row-oriented engines must scan the entire row off disk, causing memory thrashing.

We implemented a 3-tier Medallion Architecture with ClickHouse as our conformed Silver Layer for four specific technical capabilities:
1. Column-Oriented Compression: Repetitive columns compress at 4.8x, reducing row size to 76 bytes.
2. Native HyperLogLog (uniqExact): Calculates exact distinct users across billions of rows in 71 milliseconds.
3. Atomic Partition Swap: REPLACE PARTITION updates partition metadata in 15ms without locking the active table.
4. Tiered Storage: Allows old partitions to age out to S3/GCS while remaining queryable."

Q02

What is Column Shredding, and why is storing raw JSON a fatal mistake in Big Data?

⚠️ TRAP: Thinking JSONB in Postgres is fast enough for enterprise analytics.
▼

"Storing raw JSON blobs forces the database to repeat every field name string on every single row. In our v1 system, the raw jsonb column accounted for 88% of our entire disk storage (2,690 bytes out of 3,024 bytes per row).

Column Shredding decomposes the JSON into typed columns and four typed Maps: params_str, params_int, params_float, and user_props_str. This eliminated field name duplication, cut storage by 39.6 times, and turned expensive JSON array unnesting into single-column lookups."

Q03

How does ALTER TABLE ... REPLACE PARTITION work, and why is it superior to SQL transactions?

⚠️ TRAP: Not explaining that it is a filesystem metadata pointer swap.
▼

"In traditional databases, loading a day requires a long-lived transaction: DELETE FROM events WHERE date = X; INSERT ...; COMMIT;. This holds table locks for hours, blocks concurrent readers, and crashes if the network blips.

In ClickHouse, ALTER TABLE events REPLACE PARTITION (app_id, event_date) FROM events_staging is an atomic, O(1) metadata operation. It swaps disk directory hard links in under 15 milliseconds. Dashboards never experience table locks during the 4-hour ingestion read, and data visibility is instant."

Q04

How do you prevent ClickHouse Code 209 (receive_timeout) during massive data loads?

⚠️ TRAP: Suggesting increasing receive_timeout to several hours instead of fixing the architecture.
▼

"Increasing timeouts is a fragile workaround. Code 209 happens when a client opens an insert connection and appends to it while reading from a slow remote API.

We solved this by decoupling the read and send clocks in Go: we accumulate a full 50,000-row batch in local RAM first using zero-allocation slice reuse (buf = buf[:0]). Once full, we open the ClickHouse batch, transmit the 50k rows over the local network in under 150ms, and close it. Resetting slice length without re-allocating memory ensures zero Garbage Collection pauses. BigQuery network latency never touches the database connection timer."

Q05

How do you handle duplicates in streaming GA4 exports without paying extra query costs?

⚠️ TRAP: Suggesting unnesting event_params or using ClickHouse ReplacingMergeTree.
▼

"GA4 streaming intraday tables exhibit a ~0.64% duplicate rate. ReplacingMergeTree in ClickHouse only deduplicates eventually during background merges, causing non-deterministic counts on live dashboards.

We filter duplicates upfront in BigQuery using QUALIFY ROW_NUMBER() OVER (...) = 1 partitioned across the five native batch coordinates: user_pseudo_id, event_name, event_timestamp, event_bundle_sequence_id, and batch_event_index. All five are top-level scalar columns, scanning zero extra query bytes."

Q06

Why build derived rollups manually instead of using ClickHouse Materialized Views?

⚠️ TRAP: Assuming Materialized Views are always the best practice in ClickHouse.
▼

"ClickHouse Materialized Views act as insert triggers on incoming blocks. If you re-sync a day (due to a backfill or error), the Materialized View appends duplicate aggregated values.

We built our rollups (like user_daily) as an explicit step inside the day's load pipeline using staging + REPLACE PARTITION. When a day re-syncs, its rollups are completely overwritten cleanly, guaranteeing strict idempotency and zero duplicate counts."

Q07

Why store sync_state in Postgres instead of inside ClickHouse?

⚠️ TRAP: Forgetting that ClickHouse is an OLAP engine without ACID transaction isolation.
▼

"Sync state requires ACID guarantees: row-level locking, unique primary keys, and immediate read-after-write consistency. ClickHouse is an OLAP engine designed for append-only columnar analytics; it does not offer row-level locking.

Storing sync_state in Postgres ensures that concurrency status transitions (running, hot, success, failed) are strictly consistent, preventing two workers from syncing the same day simultaneously."

Q08

Explain the 'Swap First, Mark Later' principle. What happens if the process crashes?

⚠️ TRAP: Thinking marking success first is safer.
▼

"ClickHouse and Postgres cannot share a distributed transaction. If we marked 'success' in Postgres before the ClickHouse partition swap, a crash would leave the database recording a day as loaded when it never arrived.

By swapping in ClickHouse first, then marking in Postgres, a crash between the two simply results in the next cycle re-syncing the day. Because the partition swap is idempotent, a redundant reload has zero side effects."

Q09

How does the pipeline automatically detect and self-heal Google Analytics backfills?

⚠️ TRAP: Re-querying all historical data tables with full scans every day.
▼

"Full table queries would incur enormous BigQuery costs. Instead, we query BigQuery table metadata, which is completely free.

Every cycle, the engine compares the table's current lastModifiedTime with the timestamp recorded in Postgres when the day was sealed. If Google backfilled data into a historical day, the timestamp mismatch triggers a clean re-load of that partition automatically."

Q10

Why does ClickHouse ORDER BY end with user_pseudo_id?

⚠️ TRAP: Not understanding how sparse index granules work in MergeTree.
▼

"In ClickHouse, the primary index is sparse with index_granularity = 8192 (writing one index mark into the .idx file for every 8,192 rows). By ordering by (app_id, event_date, event_name, user_pseudo_id), events for a single user are clustered together on disk within that event type.

When support or analytics investigates an individual user, ClickHouse executes a tight range scan over a few disk blocks rather than scanning the entire multi-gigabyte day partition."

Q11

What are Materialized Columns in ClickHouse, and when should they be used?

⚠️ TRAP: Confusing Materialized Columns with Materialized Views.
▼

"Materialized Columns are calculated once during insertion and stored as real physical columns on disk (e.g. session_id Int64 MATERIALIZED params_int['ga_session_id']).

They should be used for hot parameters that appear on almost every dashboard query. This gives you the flexibility of typed Map lookups for arbitrary custom parameters, combined with native physical column scan performance for primary KPIs."

Q12

How do you handle user sessions that cross midnight in daily partitioned data?

⚠️ TRAP: Assuming session metrics can only be computed within single-day partitions.
▼

"Mobile sessions starting at 23:55 and ending at 00:15 span two date partitions. In our pipeline, the function prevDayFlowDue() tracks when today's intraday data lands and triggers an auxiliary rebuild of yesterday's flow facts.

This ensures that session duration, exit screens, and conversion funnels incorporate evidence from the trailing day without requiring full historical re-computation."

Q13

Why use LowCardinality(String) instead of plain String columns?

⚠️ TRAP: Using LowCardinality on high-cardinality fields like user IDs or UUIDs.
▼

"For columns with fewer than 10,000 distinct values (like country, platform, event_name), LowCardinality replaces repeated string values with a dictionary of 1-byte or 2-byte integer IDs.

This drastically reduces disk usage and accelerates GROUP BY queries by executing integer comparisons instead of string hashing."

Q14

How do you safely delete source tables in BigQuery (DELETE_AFTER_SYNC)?

⚠️ TRAP: Deleting source data immediately after the insert command returns.
▼

"We enforce five strict defense-in-depth gates before deleting:
1. The partition swap is confirmed in ClickHouse.
2. Inserted row count matched BigQuery reported rows.
3. BigQuery table metadata remained unchanged during load.
4. A post-swap live count() on ClickHouse matches the written rows.
5. Table name strictly validates against ^events_\d{8}$ regex (never deleting intraday tables)."

Q15

How do you compute median step-times in conversion funnels without distortion?

⚠️ TRAP: Calculating median(Step2) minus median(Step1).
▼

"Subtracting medians of two steps produces mathematical anomalies (and can even yield negative durations if user populations differ).

We calculate pairwise time differences inside each individual user session first (Step2 arrival minus Step1 arrival), and then execute quantileExact(0.5) over those valid time differences, dropping sessions that skipped steps or completed them out of order."

Q16

Why use sentinel date 1970-01-01 (toDate(0)) instead of NULL?

⚠️ TRAP: Forgetting that Nullable columns add memory bitmasks in columnar engines.
▼

"In ClickHouse, Nullable columns require an extra null-mask byte per row, degrading vectorized SIMD query optimization and compression efficiency.

Using 1970-01-01 as a sentinel value for unknown dates avoids the nullable bitmask entirely and compresses cleanly into zero bytes under run-length encoding."

Q17

How do you prevent race conditions between staging tables during concurrent source loads?

⚠️ TRAP: Truncating the staging table while another worker is writing to it.
▼

"For the main events_staging table, concurrency is safe because REPLACE PARTITION (app_id, event_date) only touches the specific named partition.

For auxiliary rollup staging tables that require full truncation, we serialize operations using an in-memory swapMu sync.Map per table in Go, preventing concurrent workers from clearing each other's staged data."

Q18

What happens if a day in BigQuery is genuinely empty? How does the pipeline handle it?

⚠️ TRAP: Running REPLACE PARTITION from an empty staging table.
▼

"ClickHouse strictly prohibits REPLACE PARTITION from an empty source table to prevent accidental data erasure.

Our code explicitly checks if written == 0. In that case, it skips the swap and directly executes ALTER TABLE events DROP PARTITION (app_id, event_date) to achieve the correct empty state cleanly."

Q19

How does the A/B testing engine verify Sample Ratio Mismatch (SRM)?

⚠️ TRAP: Comparing variant metrics without testing whether traffic allocation is statistically valid.
▼

"If a 50/50 A/B test delivers 60% of users to variant A, calculating metric uplift is statistically invalid due to traffic bias.

Our engine runs a Chi-square goodness-of-fit test on observed user counts per variant versus expected allocation weights. If the p-value falls below 0.001, it flags an SRM violation in verdict_code, alerting teams before decisions are made on tainted data."

If you were redesigning this data engine from scratch, what would you add next?

Q21

Why did you NOT use Apache Spark, Kafka, and Airflow? Isn't that the industry standard Big Data stack?

⚠️ TRAP: Saying 'we did not have time' or 'we did not know Spark'. A Staff Engineer justifies architectural minimalism through workload sizing, compute pushdown, and operational TCO.
▼

"We deliberately avoided the 'Enterprise Resume-Driven Development' trap. Introducing Spark, Kafka, and Airflow for this pipeline would have created massive operational bloat, higher cloud infrastructure bills, and worse latency:

1. Why NOT Apache Spark? (Compute Pushdown & C++ Vectorisation):
Our volume is 4M to 50M rows per day per tenant (billions per year). Spark is designed for multi-node distributed MapReduce across petabytes where data exceeds single-node capacity. For our scale, we pushed deduplication down to BigQuery's serverless engine via QUALIFY ROW_NUMBER() = 1 ($0 extra scan cost), and loaded into ClickHouse's C++ SIMD vectorised engine, which aggregates 100M+ rows/second on a single server — 5x to 10x faster than Spark JVM overhead without paying for idle EMR/Databricks clusters.

2. Why NOT Apache Kafka? (Avoiding the Double-Hop Anti-Pattern):
GA4 mobile devices already stream directly into Google Cloud BigQuery intraday tables. BigQuery is already a globally distributed, durable buffer. Inserting Kafka between BigQuery and ClickHouse would create an unnecessary broker hop (Mobile → BigQuery → Kafka → ClickHouse), serializing/deserializing twice, managing ZooKeeper/KRaft quorum, and monitoring consumer lag. In addition, ClickHouse is built specifically for 50k-row batch bursts, not row-by-row streaming.

3. Why NOT Apache Airflow? (Lean Ingestion Daemon over Operational Bloat):
Airflow requires a webserver, scheduler daemon, Celery worker pool, and Redis/RabbitMQ broker. Our Go ETL daemon is a single 20MB compiled binary that runs as a lightweight Kubernetes CronJob or background ticker. It uses PostgreSQL etl.sync_state for atomic row-level state machine transitions. It provides zero-overhead, sub-second error recovery without the massive operational maintenance of Airflow.

Senior engineering is about choosing the leanest, most reliable architecture for the business problem, not stacking unnecessary buzzwords."
