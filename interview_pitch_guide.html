"In my second major project, 4SCAMPAIGN—an automated outbound call platform for enterprise clients in Japan—we faced a massive concurrency challenge when scaling to 100,000 calls per campaign.

2. Because thousands of call events were firing at the same time, Twilio webhooks often arrived out of order. Here is how I architected the fix:

When the late 'Answered' event arrived 10 milliseconds later, the system saw that state 3 was lower than state 4—so it safely recorded the timestamp for analytics without rolling back the call status!

The result:
Our platform reliably processed over 100,000 concurrent calls without a single server crash, reduced internal service latency by 30%, and achieved 100% accurate billing for our Japanese customers."

Q1 • Payment System

"Design a payment processing system that handles high concurrency and guarantees no duplicate transactions."

I'd design it around three guarantees: idempotency, distributed locking, and an async workflow engine.

Every payment request carries a unique idempotency key. The API layer checks Redis first — if that key already exists, we return the cached result immediately without touching the database. No duplicates.

For the actual charge, we use optimistic locking on the account balance row — we only commit if the version number hasn't changed. If two requests race, only one wins; the other retries cleanly.

Long-running steps — like calling a payment gateway, updating ledgers, and sending notifications — run as a Temporal workflow. Each step is retryable and resumable, so a server crash mid-payment doesn't leave money in an unknown state.

Layer 1 — API Gateway: Idempotency

Every payment request from the client includes a unique idempotency key (typically a UUID generated client-side). Before doing anything, the API checks Redis: Has this key been processed?

  • If yes: return the cached response immediately. The client gets a consistent result even on retry.
  • If no: reserve the key in Redis with a short TTL (like 24 hours) and proceed.

This eliminates the vast majority of duplicate-charge scenarios caused by client retries or network timeouts.

Layer 2 — Database: Optimistic Locking

For the account balance update, I use optimistic locking with a version column in PostgreSQL:

UPDATE accounts SET balance = balance - amount, version = version + 1 WHERE id = ? AND version = ?

If two concurrent requests race, one sees 0 rows affected — meaning another transaction already updated that row — and retries. This avoids the performance cost of row-level pessimistic locks while still being race-condition safe.

Layer 3 — Workflow Engine: Temporal

Payment isn't a single DB write — it's a multi-step saga: debit account → call payment gateway → credit counterparty → update ledger → send notification. Any of these steps can fail.

I orchestrate this as a Temporal workflow. Each activity is retryable with backoff. If the server crashes mid-payment, Temporal replays the workflow from the last successful checkpoint. The customer never ends up in a "money deducted but payment not confirmed" state.

This is exactly the pattern I used in the ONE E-Payment project — and it's what let us handle millions of transactions with near-zero inconsistency incidents.

Q2 • Rate Limiting

"How would you design a distributed rate limiter that works across multiple API servers?"

I'd use the sliding window counter algorithm backed by Redis — because Redis is single-threaded and atomic, which solves the distributed coordination problem cleanly.

The key idea: for each user or IP, store a sorted set in Redis where each member is a request timestamp. On every request, we remove old timestamps outside the window, count what's left, and either allow or reject — all in one atomic Lua script.

This scales horizontally: any API server hits the same Redis, so rate limits are enforced globally, not per-server.

For even higher throughput, I'd add a local token bucket cache per server as a first pass — only calling Redis if the local budget is exhausted. That cuts Redis round-trips by 80% under normal load.

Algorithm Choice: Sliding Window Counter

There are 4 common algorithms — fixed window, sliding window log, sliding window counter, and token bucket. I typically choose sliding window counter for production because it's accurate, memory-efficient, and easy to reason about.

Fixed window has a well-known edge case: a user can send 2x the allowed requests by timing requests at the window boundary. Sliding window eliminates that without needing to store every individual timestamp.

Implementation: Redis + Atomic Lua Script

Each rate limit check is an atomic Lua script that does three things in one round-trip:

  1. Remove all timestamps older than the current window
  2. Count remaining requests
  3. Add the current timestamp if under the limit, or return 429

Because Redis executes Lua scripts atomically, there's no race condition — even with 50 API servers all hitting Redis simultaneously.

Response headers include X-RateLimit-Remaining and Retry-After so clients can back off gracefully instead of hammering the API.

Optimization: Local Token Bucket Cache

Under heavy load, hitting Redis on every single request adds latency. The optimization: each API server maintains a local token bucket in memory with a small quota (say 10% of the global limit). Only when the local bucket is exhausted do we call Redis to "refill" it.

This means most requests are handled in microseconds locally. Redis only gets called when a user is approaching their actual limit — reducing Redis traffic by 70-80% under normal load while keeping enforcement accurate where it matters.

Q3 • Caching

"When should you use cache, and how do you avoid cache inconsistency in a system with high write traffic?"

I cache data when it's read far more often than it's written — like user profiles, config, or product catalog. I avoid caching anything that must always be real-time accurate, like account balances.

The pattern I always start with is Cache-Aside: read from cache first, fall back to DB on miss, then write to cache. Simple and battle-tested.

For high-write scenarios, the main risk is stale data. My solution: short TTLs plus event-driven invalidation. When data changes, publish an event to a message queue. Cache consumers receive it and evict the key immediately. Short TTL is the safety net if the event gets lost.

I also watch out for cache stampede — a thundering herd when a popular key expires. I prevent this with a mutex lock and probabilistic early expiry.

When to Cache (and When NOT to)

Cache is a trade-off between speed and consistency. I cache when the data is: read-heavy, expensive to compute or fetch, and tolerates slight staleness. Classic examples: user session data, product listings, config flags, aggregated dashboard metrics.

I don't cache: real-time account balances, inventory counts in a flash sale, or anything where showing stale data creates a business or legal problem.

Cache-Aside + Write-Through Pattern

Cache-Aside is my default: on read, check cache → miss → query DB → populate cache. Simple, lazy, works everywhere.

For write-heavy but still cacheable data, I layer on Write-Through: every write goes to both cache and DB atomically. This keeps cache always fresh but doubles write latency. I use it selectively — not globally.

For very heavy writes where DB throughput is the bottleneck, Write-Behind (write to cache first, async flush to DB) dramatically reduces DB load — but adds risk if the cache node dies before flushing. I only use Write-Behind with Redis persistence enabled and careful monitoring.

Handling Inconsistency: Event-Driven Invalidation

Short TTL alone isn't enough when correctness matters. My preferred approach: event-driven cache invalidation.

When a write happens, the service publishes a data.updated event to a message queue (Kafka or Redis Pub/Sub). Cache consumers listen and immediately evict or refresh the affected key. This gives near-real-time consistency without tight coupling between services.

TTL is the fallback: even if the event is lost, the cache expires on its own. Set TTL short enough to bound the staleness window but long enough that cache hit rate stays high.

Preventing Cache Stampede

When a popular key expires, hundreds of requests can hit the DB simultaneously before anyone repopulates the cache — the thundering herd problem.

Two solutions I use together: First, a mutex lock — only one request regenerates the cache; the rest wait. Second, probabilistic early expiry — slightly before the TTL hits zero, start refreshing the cache proactively, so the key never actually expires under load.

Q4 • Database Scaling

"Your PostgreSQL database is becoming a bottleneck. Walk me through how you'd scale it."

I always go in order: optimize first, then scale. Scaling a poorly-optimized database just means paying more for the same problems.

Step 1: Query optimization — add indexes, rewrite N+1 queries, use EXPLAIN ANALYZE to find slow plans. This is usually where 80% of the gains come from.

Step 2: Read replicas — route SELECT queries to replicas, keeping writes on the primary. This alone often removes the read pressure entirely.

Step 3: Connection pooling with PgBouncer — PostgreSQL has a per-connection overhead, so pooling 1000 app connections into 50 DB connections dramatically reduces memory and CPU load.

If you've done all that and still need more, then you talk about partitioning and sharding.

Phase 1 — Optimize Before You Scale

First thing I do is run EXPLAIN ANALYZE on the slowest queries. Missing indexes and N+1 query patterns are responsible for the majority of DB bottlenecks. I've seen a single compound index cut a query from 3 seconds to 8 milliseconds.

I also review table bloat (dead tuples from heavy UPDATEs), vacuum settings, and make sure connection pooling via PgBouncer is in place. Each Postgres connection consumes 5-10MB of RAM. Without pooling, 500 app instances will open 500 connections and bring the DB to its knees before any query runs.

Phase 2 — Read Replicas and CQRS

Most applications are read-heavy — 80/20 rule. Adding read replicas routes all SELECT traffic off the primary. The primary only handles writes.

I pair this with a lightweight CQRS pattern: the command side (writes) goes to the primary; the query side (reads) goes to replicas or even a denormalized read model for complex dashboard queries. This separation keeps the write path fast and the read path scalable independently.

Phase 3 — Partitioning, then Sharding (Last Resort)

Table partitioning (range or list) is usually the next step when a single table grows too large. Partitioning by date is ideal for time-series data — old partitions can be archived, queries on recent data become much faster because they only scan the active partition.

Horizontal sharding — splitting rows across multiple database instances — is the nuclear option. It solves write-throughput limits that replicas can't fix. But it makes cross-shard joins, distributed transactions, and schema migrations much harder. I only recommend it after partitioning isn't enough and the business genuinely needs it.

Q5 • Scalability

"How do you design a backend system that can scale horizontally from day one — without rewriting it later?"

Three principles I always start with: stateless services, async messaging, and smart load balancing.

Stateless first: every API server must hold zero in-memory session state. Sessions live in Redis, files go to S3. That way, any server can handle any request — adding more servers is just spinning up new instances behind the load balancer.

For workloads that can't be instant, I use an async message queue — like SQS or Kafka. The API responds immediately with a job ID; workers scale independently to consume the queue. The API layer and the processing layer scale at their own pace.

And I design for auto-scaling from day one — CPU and queue depth as trigger metrics — so the system grows automatically with traffic spikes, not after an outage.

Rule 1 — Make Every Service Stateless

The single biggest scaling blocker is server-side state. If a server stores a user's session in memory, that user is "stuck" to that server. Add a second server and you need sticky sessions — which defeats the point.

Solution: push all state out. Sessions go to Redis. User-uploaded files go to S3. Shared config goes to a config service. Now every server is identical and interchangeable. Scaling out is just launching more copies.

Rule 2 — Decouple with Async Messaging

Synchronous chains are scaling bottlenecks. If Service A calls Service B calls Service C, and C is slow, A gets slow too — no matter how many A replicas you spin up.

The fix: break the chain with a message queue (SQS, Kafka, or RabbitMQ). Service A publishes an event and returns immediately. Workers pick up events from the queue and process at their own pace. API throughput and processing throughput scale independently — each with its own auto-scaling group.

This also creates natural backpressure: if processing falls behind, the queue grows, which auto-scales workers. If the queue drains, workers scale down. No manual intervention needed.

Rule 3 — Build for Auto-Scaling, Not Manual Scaling

I configure AWS Auto Scaling Groups with two trigger metrics: CPU utilization above 70% triggers scale-out; queue depth above 1,000 messages triggers worker scale-out. Scaling in happens conservatively with a cooldown window to avoid oscillation.

I also put a CDN (CloudFront) in front of any static content and cacheable API responses. For a typical app, 40-60% of traffic is for static assets — serve those from edge and your origin servers never see them.

The result: the system handles 10x traffic spikes automatically, not reactively. Capacity grows before the user feels any slowness.

Q6 • Fault Tolerance

"How do you build a system that stays up when things go wrong — a dependency is down, a service crashes, traffic spikes unexpectedly?"

My fault-tolerance toolkit has four layers: Circuit Breaker, Retry with backoff, Graceful Degradation, and Health checks with auto-recovery.

Circuit Breaker is the most important one. If a downstream service starts failing, I open the circuit — stop sending requests immediately — and return a fallback response. Without it, your service queues up thousands of waiting requests, exhausts its thread pool, and goes down too. One failing dependency becomes a full system outage.

Retry with exponential backoff handles transient failures: network blips, short DB timeouts. But I always add jitter — random delay — so retries from 1,000 instances don't all arrive at the same second and overwhelm the recovering service.

And graceful degradation means the core feature still works even when non-critical parts are down. Show stale data, hide the recommendation widget, disable a non-essential feature — but never crash the whole page.

Pattern 1 — Circuit Breaker: Stop the Bleed

The Circuit Breaker pattern (popularized by Netflix Hystrix, now standard in Resilience4j and similar libraries) has three states:

  • Closed: normal, requests flow through
  • Open: failure rate exceeded threshold — stop all requests, return fallback immediately
  • Half-Open: after a cooldown, allow one probe request. If it succeeds, close the circuit. If not, stay open.

This prevents cascading failures: one slow service causing thread pool exhaustion that takes down your entire API layer. In production, I configure circuit breakers on every external call: payment gateways, notification services, third-party APIs.

Pattern 2 — Retry with Exponential Backoff + Jitter

Transient failures — a brief network blip, a DB connection timeout — are normal in distributed systems. Retry with exponential backoff handles them: wait 1s, then 2s, then 4s, then 8s before giving up.

The critical addition is jitter — add random noise to each retry delay. Without jitter, all 1,000 retrying instances hit the recovering service at exactly the same second, creating a retry storm that re-kills the service. With jitter, they spread out organically.

I also set a max retry count and make sure the operation is idempotent before enabling retries. Retrying a non-idempotent operation (like charging a card) without idempotency keys is dangerous.

Pattern 3 — Graceful Degradation and Fallbacks

Graceful degradation means the system delivers partial functionality rather than failing completely when a component is down.

Practical examples from my experience: if the recommendation engine is down, show a static "popular items" list from cache. If the notification service is down, log the notification for later delivery rather than blocking the checkout flow. If the analytics service is slow, skip it and record the event to a queue asynchronously.

The key mindset: separate critical path (what the user absolutely needs to complete their action) from non-critical enrichment (what's nice to have). Only the critical path needs to be synchronous and blocking.

Pattern 4 — Health Checks, Readiness, and Auto-Recovery

Every service exposes a /health endpoint that checks DB connectivity, Redis connectivity, and queue depth. The load balancer polls this every 10 seconds. If a node fails two consecutive checks, it's removed from rotation automatically.

I also distinguish liveness (is the process alive?) from readiness (is it ready to serve traffic?). During startup or DB migration, a service can be live but not ready — the load balancer should skip it until it's fully initialized. This prevents "deployment flaps" where half-started instances receive traffic they can't handle.

Q7 • Cloud Cost Optimization

"Your AWS bill is 3x higher than expected. How do you find the waste and cut costs without hurting performance or reliability?"

I start with AWS Cost Explorer and sort by service — usually EC2, RDS, and data transfer are the top three cost drivers. Then I look for the obvious waste first.

The classic wins: right-size over-provisioned instances — most teams provision for peak and forget to scale down. Switch stable, predictable workloads from On-Demand to Reserved Instances or Savings Plans — that alone saves 30-60%.

For batch jobs and non-critical workers, use Spot Instances — same compute at 70-90% discount. For data transfer costs, push static assets to CloudFront CDN — edge delivery is far cheaper than origin bandwidth.

Finally, set up S3 lifecycle policies to automatically move old data to Glacier, and kill unused resources — orphaned EBS volumes, old snapshots, and idle load balancers add up fast.

Step 1 — Visibility: Find Where the Money Goes

Before cutting anything, I get clarity. I use AWS Cost Explorer with tag-based filtering to see costs by service, by environment (prod vs dev/staging), and by team. Most teams discover that dev/staging environments cost 30-40% of production — and run 24/7 even when no one is using them.

Quick win: schedule dev environments to shut down overnight and on weekends. That's an instant 60% saving on non-prod compute with zero performance impact on production.

Step 2 — Right-Size and Commit for Savings

Right-sizing means matching instance size to actual usage. AWS Compute Optimizer analyzes CloudWatch metrics and recommends smaller instance types when CPU or memory utilization is consistently low. Teams often over-provision by 2x "just to be safe" and never revisit it.

For stable, predictable workloads — like your primary API servers and RDS database — switch from On-Demand to 1-year Reserved Instances or Compute Savings Plans. This typically cuts those line items by 30-40% with no change to the architecture.

For batch processing, background workers, and ML training jobs that can tolerate interruption: Spot Instances run identical hardware at 70-90% discount. I always design these workloads to be interruptible and resumable — which on AWS with Temporal or SQS is straightforward.

Step 3 — Cut Data Transfer and Storage Waste

Data transfer costs are the hidden bill killer. Traffic from EC2 to the internet is charged per GB. Putting CloudFront CDN in front of your API and static assets moves serving to AWS edge locations — data transfer from CloudFront to users costs a fraction of EC2 outbound. For high-traffic apps this can cut bandwidth costs by 50-70%.

For S3 storage: set lifecycle rules to automatically tier data — recent objects stay in S3 Standard, objects older than 30 days move to S3-IA (Infrequent Access), objects older than 90 days archive to Glacier. Same data, 60-80% cheaper storage cost.

And audit zombie resources regularly: orphaned EBS volumes from deleted EC2 instances, old AMI snapshots, idle NAT Gateways, and forgotten load balancers. In a team that's been building for 2+ years, these can easily add up to hundreds of dollars per month for nothing.

Step 4 — Build a Cost Culture, Not Just a Cost Sprint

One-time cleanups always regress. The sustainable fix is building cost awareness into the engineering process: tag every resource with the owning team and service, set AWS Budget Alerts so engineers see when their service crosses a threshold, and do a monthly FinOps review where cost anomalies are treated as bugs — not finance problems.

I've seen teams cut AWS bills by 40% in 3 months purely through visibility, right-sizing, and scheduling — before touching any architecture. Architecture-level changes like moving to Lambda or splitting databases come later, when the quick wins are exhausted.

Q8 • Real-Time System

"Design a notification system that delivers real-time alerts to millions of users across push, email, and in-app channels — reliably, at scale."

I'd separate the system into three parts: a producer layer that publishes events, a fan-out worker layer that routes to the right channels, and a delivery layer that integrates with third-party providers like FCM, SendGrid, and WebSocket gateways.

When something happens — a payment completes, a friend sends a message — the originating service publishes one event to Kafka. Fan-out workers consume that event and figure out: who needs to be notified? Through which channel? Right now, or can it wait?

In-app real-time alerts go through WebSocket connections or Server-Sent Events. Push notifications go through FCM/APNs. Email goes through SendGrid or SES, batched and rate-limited to stay within provider limits.

All delivery attempts are logged. Failed deliveries retry with backoff. Users who are offline get their notifications queued and delivered when they reconnect.

Layer 1 — Event Producer: Decouple Everything

The origin service (payment, chat, social) should not know or care about notifications. It publishes a single domain event: payment.completed, message.received. That's it.

Kafka is the backbone here because it handles millions of events per second, retains events for replay, and lets multiple consumer groups read the same stream independently. The notification system is just one consumer — analytics, audit logs, and fraud detection are others.

Layer 2 — Fan-Out Workers: Route and Prioritize

Fan-out workers consume events from Kafka and apply user preferences and business rules: is this user subscribed to this notification type? What channels are enabled — push, email, in-app? Is this high-priority (payment failure) or low-priority (weekly digest)?

High-priority notifications go to a dedicated high-priority queue — processed by dedicated workers with no competition from bulk email blasts. Priority queues ensure a payment failure alert is never delayed because a marketing campaign is consuming all worker capacity.

Fan-out also handles deduplication: if the same event triggers multiple notification rules, the worker consolidates them into one message rather than sending three separate pings in a row.

Layer 3 — Delivery: Channel-Specific Handlers

In-app real-time: Users maintain a persistent WebSocket connection to a notification gateway (or Server-Sent Events for simpler use cases). When a notification arrives, the gateway looks up which server holds that user's connection and pushes it directly. For users who are offline, notifications are stored in a DB and synced when they reconnect.

Push notifications: Routed to FCM (Android) or APNs (iOS) via a provider wrapper. I always store the delivery receipt — delivered, failed, opened — and retry on failure with exponential backoff. Tokens expire; the system must handle token refresh gracefully.

Email: Sent through AWS SES or SendGrid, rate-limited to respect provider sending limits and avoid spam flags. Bulk emails (weekly digests) are batched and scheduled during off-peak hours to minimize cost and maximize deliverability.

Reliability: Delivery Guarantees and Observability

Every notification is written to a delivery log before dispatch — status: pending. On success: delivered. On failure after max retries: dead-letter queue for manual review. This gives full auditability: for any notification, I can tell you exactly when it was generated, when it was sent, and whether the device confirmed receipt.

I also expose metrics: delivery success rate per channel, p99 delivery latency, dead-letter queue depth. Alerts fire if any channel's success rate drops below 95% — that's usually the first signal that a third-party provider is having issues, and we can fail over to a backup provider automatically.

Situation & My Disagreement

What I took away: disagreement is a gift when you deliver it well. The key is separating the idea from the ego — make it about the best outcome for the team, not about being right. And once the decision is made, commit to it fully even if it wasn't exactly what you proposed.

CF2 • Feedback Culture

Giving feedback: I follow a simple rule — be specific, be private, be constructive. I never criticize someone's work in a group setting. I go to them directly, focus on the behavior or the code, never the person, and always pair the problem with a concrete suggestion.

For example: instead of saying "this code is messy," I say "this function does five things — if we extract the validation logic here, it becomes much easier to test and reuse. Want to pair on it?" That's a conversation, not a judgment.

Receiving Critical Feedback

My process: listen fully without interrupting, then ask one clarifying question — "Can you give me a specific example?" This does two things: it helps me understand exactly what they mean, and it signals that I'm taking it seriously rather than dismissing it.

Then I act on it and close the loop. If a Tech Lead gives me feedback that my PRs are too large and hard to review, I split my next three PRs into smaller chunks and explicitly reference the feedback in the PR description. That closes the loop: the person who gave feedback sees it working, and they're more likely to give me feedback again in the future — which is what I want.

Giving Difficult Feedback

My framework is: Situation → Behavior → Impact → Question.

Instead of: "Your code is bad."
I say: "In the payment handler we reviewed yesterday (Situation), the retry logic doesn't have an idempotency check (Behavior) — if the client retries, we risk charging the user twice (Impact). I think adding an idempotency key here would fix it cleanly. Want to pair on the approach? (Question)"

This framework keeps the feedback factual and specific, makes the impact clear without being dramatic, and ends with a collaborative offer rather than a verdict. The person leaves the conversation with a concrete next step, not just bruised confidence.

I also always give difficult feedback privately, never in code review comments visible to the whole team. Public criticism — even when technically correct — damages trust and makes people defensive. A private conversation achieves the same result and preserves the relationship.

FU1 • ONE E-Payment: Rớt Webhook & SAP Bảo Trì

"In your ONE E-Payment project, what happens if the bank webhook is dropped over the network, or if SAP S/4HANA goes down for 12 hours after the customer has already paid?"

We never rely on a single webhook. I designed a three-layer safety net so we never lose a single payment.

First is the Fast-Path Webhook, which clears 99% of payments in under a minute. Second, if a webhook is dropped and a payment stays pending for more than 3 minutes, a background job triggers an Active Bank Inquiry API to pull the exact payment status directly from HSBC.

Third, at midnight, we run MT940 and CAMT.053 bank statement reconciliation to catch any remaining edge cases.

And if SAP goes down for 12 hours, our Temporal workflow simply pauses and retries with exponential backoff. Because Temporal stores the exact workflow state on disk, the moment SAP comes back online, all queued payments clear automatically without any human intervention.

1. Three-Layer Protection Against Dropped Webhooks

In enterprise fintech, networks fail all the time, so we never trust webhooks alone. I built a three-tier recovery architecture:

Tier 1 (Fast-Path Webhook): In 99% of cases, our Go broker receives the HSBC webhook in 4 milliseconds and triggers the Temporal workflow immediately.

Tier 2 (Active Inquiry Fallback): When a checkout session is created, we start a timer. If we don't receive a bank webhook within 3 minutes, our worker proactively calls the bank's Order Inquiry API to check if the customer's money was deducted. If the bank says paid, we trigger the exact same Temporal workflow using the same idempotency key.

Tier 3 (Nightly MT940 / CAMT.053 Reconciliation): Every night, banks send an official electronic bank statement file to our SAP server. This acts as the ultimate financial audit to ensure 100% ledger accuracy.

2. Surviving a 12-Hour SAP S/4HANA Outage

Core SAP systems regularly go down for weekend maintenance. If a customer pays while SAP is offline, we never fail their payment.

First, we record the payment as 'Paid - Pending Clearing' in MongoDB so the customer immediately sees their money is safe. Second, our Temporal workflow pauses at the SAP clearing step and retries automatically with exponential backoff. Because Temporal is a durable execution engine, that workflow can sleep safely for 12 or even 24 hours. As soon as SAP comes back up, Temporal finishes clearing the invoice and releases the container automatically.

FU2 • ONE E-Payment: Tại sao chọn Temporal.io?

"Why did you choose Temporal.io for payment orchestration instead of just using standard message queues like RabbitMQ or Kafka?"

Kafka and RabbitMQ are great for moving data from A to B, but they are stateless pipes. They don't track which step a multi-stage payment is currently on.

Our payment flow has 6 steps across multiple systems: verify bank payment, validate tax documents with AI, clear SAP invoices, release the port container, and trigger a compensating refund if something fails.

If we used plain queues, we would have to build our own database state tables, retry timers, and dead-letter recovery logic. Temporal.io gives us durable state orchestration out of the box—every step, timer, and rollback is tracked in one place with full visibility.

Choreography (Queues) vs. Orchestration (Temporal)

I actually use both—RabbitMQ for simple async tasks, and Temporal.io for complex multi-step business sagas. Here is why plain queues weren't enough for ONE E-Payment:

1. Avoiding "Queue Spaghetti": We operate across 12+ countries, each with different steps—like AI tax verification in Thailand, e-GUI tax invoices in Taiwan, and SAP clearing. With plain queues, you end up with 10 separate queues and dead-letter topics. When a payment gets stuck at step 4, debugging across 5 microservices is a nightmare.

2. Built-in Saga Rollbacks & Long Timers: Some workflows need to sleep for hours—for example, waiting for a human accountant to approve a flagged tax form, or running a compensating refund if SAP rejects an order. Temporal lets us write that entire workflow as clean, sequential code while it handles persistence, retries, and crash recovery under the hood.

FU3 • 4SCAMPAIGN: Xử lý 100,000 cuộc gọi & Loạn thứ tự Webhook

"In 4SCAMPAIGN, when running 100,000 concurrent calls, what happens if Twilio sends status webhooks out of order—for example, the 'Call Completed' event arrives before the 'Keypad Pressed' event?"

That actually happened a lot under high concurrency! I solved it using three mechanisms: strict state-machine transition rules, Redis per-call locking, and monotonic sequence timestamps.

First, every webhook for a specific `callSid` acquires a short Redis lock for that call so two webhooks for the same call never overwrite each other at the same millisecond.

Second, our state machine only allows valid forward transitions—like `RINGING` to `ANSWERED` to `COMPLETED`. If a late `RINGING` event arrives after the call is already `ANSWERED`, the state machine ignores the status regression while still appending the raw event to our audit log so we never lose keypad data.

How We Prevented Race Conditions Across 100,000 Calls

When a user answers a call, presses '1', and hangs up immediately, Twilio fires three webhooks within a few milliseconds. Over the internet, they often arrive out of order. Here is how I engineered the handler to be 100% bulletproof:

1. Per-Call Distributed Lock (`lock:call:{callSid}`): We don't lock the whole database, only the specific `callSid` in Redis for a few milliseconds. This serializes concurrent webhooks for the same phone call.

2. Forward-Only State Machine: Each call state has a numerical weight (`INITIATED=1`, `RINGING=2`, `IN_PROGRESS=3`, `COMPLETED=4`). An incoming webhook can only advance the call state if its weight is higher than the current state. So a delayed `RINGING` webhook will never overwrite a `COMPLETED` call.

3. Decoupled Keypad Capture: Even if the `COMPLETED` webhook arrives slightly before the `KEYPAD_PRESSED` webhook, we store keypad inputs in an independent event array on the call document. That way, the user's survey answer is still recorded accurately even after the call has ended.

TECH1 • Node.js Event Loop, Non-Blocking I/O & Xử lý Tác vụ Nặng CPU

1. "Node.js is single-threaded. How does it handle high concurrency (like 100,000 calls), and what do you do when a task is CPU-heavy?"

"In Node.js, only the JavaScript Event Loop is single-threaded, while heavy I/O tasks—like database queries, Redis calls, and network requests—are handed off to the OS kernel and libuv thread pool in the background. Because the main thread never waits for I/O, one Node.js process can easily handle thousands of concurrent requests.

However, if a task is CPU-heavy—like parsing a huge CSV file or running AI data processing—it will block the Event Loop and freeze the server. To prevent that, I use Node.js Streams for large files, offload background jobs to BullMQ workers, or delegate heavy compute to a Python or Go microservice via gRPC."

"That is a classic question, and it is actually the exact reason why our Node.js backend in 4SCAMPAIGN could handle 100,000 concurrent calls smoothly.

1. How Node.js handles high concurrency on a single thread:
Even though JavaScript runs on a single main thread, 95% of backend work is I/O-bound—waiting for MongoDB, Redis, or external APIs like Twilio and Adyen. When Node.js makes a database or network call, it doesn't sit there waiting. It hands the task over to the libuv C++ library and the OS kernel, and immediately moves on to serve the next user. When the database finishes, it pushes a callback to the Event Loop. That non-blocking I/O design lets Node.js handle massive concurrent traffic with very low memory overhead.

2. What I do when a task is CPU-heavy (Protecting the Event Loop):
The golden rule of Node.js is: never block the Event Loop. If one user triggers a heavy CPU task—like parsing a 100MB Excel file, encrypting large payloads, or running heavy math—the single thread gets stuck and every other user gets a timeout.
In production, I solve CPU-bound work in three practical ways:
• First, for large data files (like importing 100,000 phone numbers), I never use `JSON.parse` on the whole file in memory—I use Node.js Streams to process data chunk by chunk without blocking the Event Loop.
• Second, for medium CPU tasks inside Node.js, I use Worker Threads or push the job into a BullMQ background worker process so the main API server stays 100% responsive.
• Third, for heavy data analytics or AI processing, I offload the work entirely to a Python FastAPI or Go service via gRPC."

TECH2 • Chẩn đoán & Xử lý Tràn Bộ Nhớ (Memory Leak & OOM Kill)

2. "How do you detect and fix a memory leak or Out-Of-Memory (OOM) crash in a Node.js production service?"

"To catch a memory leak, I first check our Grafana and Prometheus metrics for a 'sawtooth' pattern where V8 heap memory keeps climbing and never drops after garbage collection.

To find the exact line of code, I take two V8 Heap Snapshots a few minutes apart and compare them in Chrome DevTools to see which objects are growing in memory.

In my experience, 90% of Node.js memory leaks come from three culprits: loading huge database queries into RAM without cursors or streams, storing data in unbounded in-memory Maps/caches instead of Redis, or forgetting to remove event listeners and timers."

"I actually solved a real Out-Of-Memory (`OOMKilled`) issue on Kubernetes in our campaign export service. Here is my step-by-step process for finding and fixing memory leaks in Node.js:

1. How I detect and isolate the leak:
First, I monitor `process.memoryUsage().heapUsed` in Prometheus and Grafana. In a healthy service, memory goes up and drops back down when the V8 Garbage Collector runs. In a memory leak, the graph climbs steadily like a staircase until Kubernetes kills the pod.
To pinpoint the exact object, I take two V8 Heap Snapshots—one at normal load, and a second one 10 minutes later—and use the Comparison view in Chrome DevTools. That shows me the exact object constructor and closure retaining the memory (`Retained Size`).

2. The 3 most common root causes I fix in production:
• Unbounded Database Loads (The #1 culprit): A developer runs `.find().toArray()` on 200,000 call records to generate a CSV report, loading hundreds of megabytes of JSON into V8 heap at once. I fix this by replacing `.toArray()` with MongoDB Cursors and Node.js Streams (`pipeline`), keeping memory flat at just 30MB regardless of file size.
• In-Memory Caching without TTL: Storing user sessions or lookup tables in a global JavaScript `Map` or object that grows forever. I fix this by moving state to Redis with strict TTLs or using an `LRU Cache` with a hard max-size limit.
• Uncleaned Event Listeners & Closures: Attaching `.on('data')` or `setInterval` inside a request handler without calling `removeListener` or `clearInterval` when the request closes."
