2 Nút "FREE" gây hiểu lầm bị lừa đảo Cờ text_policy_iap bị tắt trong Remote Config, khiến nút Paywall hiện chữ "FREE" thay vì giá thật. User mới tưởng miễn phí nên bấm vô tội vạ. 51% (071) – 62% (065) user mới bấm nút trong giờ đầu nhưng 95% hủy khi store đòi $6.99/tuần.     fun promptInAppReviewIfFirstSuccess(activity: Activity) {
    val prefs = activity.getSharedPreferences("app_rating", Context.MODE_PRIVATE)
    if (prefs.getBoolean("has_prompted_review", false)) return

    val reviewManager = ReviewManagerFactory.create(activity)
    reviewManager.requestReviewFlow().addOnCompleteListener { task ->
        if (task.isSuccessful) {
            reviewManager.launchReviewFlow(activity, task.result).addOnCompleteListener {
                prefs.edit().putBoolean("has_prompted_review", true).apply()
            }
        }
    }
}

HÀNH ĐỘNG 6 Chuẩn Hóa Khung Base A/B: Xóa Bỏ Pha Loãng Mẫu (SDK & ClickHouse)
SDK Team + Data Eng ⏱️ 1 – 1.5 tuần Kế thừa mọi app mới
  • 1
    Module AbKit trong vtmonet: Chỉ bắn event khi thấy bài test
    Viết phương thức AbKit.expose(testId, variant) trong SDK:
    object AbKit {
    fun expose(experimentId: String, variant: String, isFallback: Boolean = false) {
        val bundle = Bundle().apply {
            putString("experiment_id", experimentId)
            putString("variant", if (isFallback) "default_fallback" else variant)
        }
        Twyn.trackEvent("vt_experiment_viewed", bundle)
    }
}
  • 2
    Cập nhật Materialized View trong ClickHouse
    Sửa truy vấn trong ab.rmv_assignment: Chuyển điều kiện kích hoạt từ session_start sang vt_experiment_viewed:
    ALTER TABLE ab.rmv_assignment MODIFY QUERY
SELECT 
    app_id,
    params_string['experiment_id'] AS exp_key,
    user_pseudo_id,
    min(install_date) AS install_date,
    min(event_date) AS enrol_date,
    argMin(params_string['variant'], event_timestamp) AS variant
FROM analytics.events
WHERE event_name = 'vt_experiment_viewed'
  AND params_string['variant'] != 'default_fallback'
GROUP BY app_id, exp_key, user_pseudo_id;
🛡️ Cơ Chế Bảo Hiểm Rủi Ro: Quy Trình Leo Thang Thận Trọng (Canary Ramp-Up)

Nguyên tắc kiểm soát rủi ro diện rộng (Blast Radius) phù hợp với quy mô lưu lượng hiện tại:

Bước 1: Canary Smoke Test (5% – 10%)
Thời gian: 24h đầu.
Mục tiêu: Kiểm tra kỹ thuật thuần túy (Crash, ANR, lỗi tải Remote Config, kẹt Google Billing). Với lưu lượng ~350 user/ngày, 5% chỉ có 17 user nên tuyệt đối không dùng để phân tích tỷ lệ. Sau 24h nếu an toàn kỹ thuật $\rightarrow$ Chuyển ngay sang Bước 2.
Bước 2: Kiểm Định Tối Ưu (50 / 50)
Thời gian: 7 – 14 ngày.
Mục tiêu: Tối ưu hóa Sức mạnh Thống kê (Statistical Power 80%, Significance 95%). Ở quy mô traffic nhỏ giọt (180–350 user/ngày), tỷ lệ 50/50 là bắt buộc để gom đủ cỡ mẫu và chốt kết quả trong vòng 1–2 tuần.
Bước 3: Rollout Toàn Diện (100%)
Thời gian: Sau khi xác nhận Winner.
Mục tiêu: Gạt cờ áp dụng 100% làm cấu hình mặc định cho app và nhân bản cấu hình thắng cuộc sang các app mới trong tương lai.
